# 组合根维护边界

基础UI、球杆装配，以及动画/显示/场景、设置/AI/对局状态、输入/相机/回放三个批次均已按职责拆分并完成验收。当前模块、状态拥有者和验证方式见[游戏装配](game-composition.md)；球杆请求缓存与材质的专门契约见[球杆装配](cue-composition.md)。

`application/compose-game.js`负责捕获引擎构造器、装载具名模块、选择网址中的室内方案、按原顺序调用子装配、连接跨组依赖，以及最终导出SnookerApplication。AI模板、游戏对话框扩展、菜单和对局控制器的最终连接继续在总根维护。

## 已落实的边界

| 职责             | 维护位置                                                                      | 所有权与扩展入口                                                     |
| ---------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 动画、显示与场景 | composition中的animation、motion-animation、display-planes、game-view、scenes | 缓动定义、图集和场景定义归presentation；根调用一次，材质注册顺序保持 |
| 设置与基础对局   | compose-session、settings/local-game-settings                                 | 设置实例、控制器编号和基础模型类型由会话子装配拥有                   |
| AI与开球轮换     | compose-route-geometry、compose-ai、ai/ai-registry、compose-match-model       | 路线池、三档AI共用的规划器和开球计数分别有单一拥有者                 |
| 输入与母球放置   | compose-controls、compose-ball-in-hand、compose-cue-input                     | 按类型族保留共享临时向量；按实例保留键盘、接触和放球状态             |
| 相机与人物       | compose-orbit-camera、compose-aim-camera、compose-person                      | 相机交点缓存有独立工厂；人物连接原控制器类型                         |
| 击球与回放       | compose-player-turn、compose-replay                                           | 击球参数、回放轨道、缓冲及相机解析状态留在对应子装配                 |
| 最终应用连接     | compose-game                                                                  | 连接返回的类型、菜单、对话框及MatchController，导出应用              |

根中的CushionBody仍保留原碰撞相关运算。它属于独立领域算法范围；当前装配拆分没有同时改写碰撞数学。后续如要整理该实现，应先增加真实输入的算法刻画，再单独处理。

## 必须保持的契约

1. **延迟读取。** 显式getter读取后定义类型与活动状态；不将它们改成初始值快照。模块和模板仍在原执行位置读取，避免提前触发加载副作用。
2. **实例与对象身份。** 一个根只调用各子装配一次。设置、编号、AI规划器、路线池、开球计数和共享临时向量不能随类实例重复创建，也不能扩大为跨应用全局状态。
3. **初始化顺序。** dynamic-lighting-material注册、材质读取、场景构造、模板扩展和导出getter保留原顺序。新增功能沿用已有装配入口，先明确状态寿命与释放方式。
4. **两种运行方式。** 源码采用ES模块，构建采用受限工厂编译器；子工厂使用默认导出与相对默认导入，不引入ESM导入环。loadModule的循环导出语义仍由装载器维护。
5. **登记与层次。** runtime-catalog登记实际loadModule依赖；默认工厂导入由构建图记录。新增文件使用严格规则，没有扩展preservedSources例外。游戏参数留在src，工程config只管理工程路径与服务器。

## 验证与后续维护

三组专项测试使用根中的真实依赖getter及实际子工厂，覆盖曲线、动画完成、场景顺序、设置克隆/恢复、共享编号、AI选择、轮换、输入、相机、击球和回放。新增行为优先加在相应职责的测试中，不增加生产全局诊断对象。

[算法结构复核](../validation/algorithm-validation.md)覆盖137项保留算法，不包含组合根整体；本轮另对18组搬移声明及整个根展开子工厂与依赖getter，比较表达式、运算符、对象键与执行顺序，规范化声明种类、分组及单语句花括号，不调整初始化顺序。结构证据与实际行为证据分别记录在[游戏装配验证](../../reports/validation/game-composition.json)。

每批执行整体浏览器检查、src独立复制、原始室内五视角及室内统一专项。共享对局、AI、输入和回放批次追加默认连续玩法；最终增加WebGL恢复烟雾专项。有限连续玩法仍不覆盖完整比赛或数小时运行，软件WebGL不能证明真实GPU性能。

未来扩展按具体功能进入对应子装配，先确认依赖与状态寿命，再追加行为场景。继续拆分的依据应是明确的跨职责耦合或功能需求；不以文件长度作为单独理由。
