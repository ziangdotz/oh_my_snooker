# 房间与双人对战实施方案

状态：2026-10-11 的开发提案，尚未实施。用户已明确选择：先完成同机双人，再扩展联网房间。本文件中的网络频率、超时和容量都是待验证的设计值。

## 首版目标与入口

第一阶段提供同一台电脑、同一套键鼠、同一张球台的双人轮流比赛。两位玩家使用独立姓名、分数、罚分、单杆和击球统计，沿用当前 PCOL 规则、22 球布局与操作方式。四套室内均可使用；继续保留已经完成的相机、走位、击球节奏和像素密度优化。

从现有 One more thing... 抽屉进入 TWO-PLAYER MATCH，在原抽屉内填写两位玩家姓名并开始比赛。默认姓名为 PLAYER 1 / PLAYER 2。ROOMS 在联网阶段再开放。首页、室内选择、About 和紧凑游戏界面继续沿用当前布局。

后续 ROOMS 提供创建房间、输入房间码加入、两席准备、房主开始和联网对局。同机模式始终可以脱离房间服务运行。公网好友房作为后续交付方向，先在本机双浏览器和局域网验证同一套联网实现；公网部署位置及资源在发布阶段确定。

首版以一局比赛为单位。账户、公开匹配、排行榜、观战、聊天和多局赛制不列入本次基础实现。同机模式无需先制作虚拟房间或启动网络服务。

## 阶段一：同机双人

### 模型与控制器

新增同机对局模型，复用现有规则与计分方法，替换玩家创建方式。两席拥有稳定且不同的 ID，不修改当前本地用户资料，也不把第二位玩家伪装成 AI。开球顺序由同机比赛会话管理：首局玩家 1，再来一局交替开球，不受 Practice 或 AI 模式重开次数影响。

将对局控制器中的玩家控制器创建和当前操作者绑定整理为小范围扩展入口。新增同机控制器，共享一个本地输入与相机控制器；玩家身份与统计仍是两份数据。换人时先结束上一杆的录制、球杆动作及事件绑定，再将本地操作者绑定到模型给出的当前席位，并同步放球、瞄准、工具栏与 HUD。控制器列表中不重复加入同一个对象。

交接发生在现有模型完成判罚并进入可操作状态后。得分续杆不触发换人交接。操作权以模型的 `playerIndex` 为准，不通过 UI 自行递增。

### 操作体验

- 击球、瞄准、力度、旋转、走位与放母球沿用当前键鼠操作。
- 换人时保持当前桌面视角，回到可操作站姿，清除按键持续状态、走位惯性和上一位玩家的球杆偏移；力度恢复现有默认值。使用 HUD 状态提示当前玩家，不额外弹出每杆确认框。
- 球未停稳及判罚过程中阻止新击球。暂停、帮助、回放及返回菜单的输入不会穿透到球台。
- 同机暂停继续暂停本地比赛；回放结束后恢复实际球位、当前席位与操作状态。
- 结果显示具体玩家获胜或平局，保留现有双方统计；重开清空本局统计并交替开球。
- 姓名采用文本渲染，限制长度并处理空白与重名；重名可以自动附加席位标识。

### 同机验收

1. 两位玩家都能独立完成真实放母球、瞄准与击球，统计归属于实际操作者。
2. 分别验证得分续杆、无得分换人、犯规罚分、母球入袋后的放球及清彩结束。受控规则测试与真实击球证据分别记录。
3. 换人时长按 Space、方向键或鼠标输入不会导致额外击球、持续走位或串席位。
4. 两席均可使用暂停、回放、重开和返回菜单；换人前后回放不会回写比赛分数。
5. 验证玩家 1 获胜、玩家 2 获胜与平局的结果呈现；受控终局测试不宣称已经打完一局真实比赛。
6. Chrome / Edge、四套室内、源码 / 开发 / 生产入口完成双人专项；Practice、三种 AI 难度及现有流畅性验证继续通过。

同机验收通过后再进入房间阶段，不把联网服务作为第一阶段的前置依赖。

## 阶段二：房间与联网双人

### 房间流程

创建房间 → 分享房间码或链接 → 第二位玩家加入 → 双方场景加载完成并准备 → 房主开始 → 对战 → 结果 → 双方同意再来一局或退出。

房间固定两席，房主选择当前四套室内之一。场馆变更仅在等待阶段进行，并使准备状态失效。由于当前室内切换采用整页重载，先保存房间恢复凭据；重载后恢复原席位，再重新确认资源就绪。开局后固定场馆。

区分房间状态（等待、加载、准备、比赛、结果、关闭）与比赛状态（放球、瞄准、击球、判罚、结束），避免把断线当成输赢或把场景尚未加载当成已准备。

### 推荐架构

浏览器保留 Babylon 场景、本地相机、走位、瞄准预览及输入；Node 房间服务管理席位、准备与消息顺序；隔离的比赛执行实例拥有权威球位、得分、罚分和球权。

建议使用浏览器原生 WebSocket 与 Node 服务端 WebSocket 实现。服务端可选 `ws`，只在联网服务中引入并锁定版本；其官方说明提供独立服务、HTTP 升级和连接存活检查：[ws 官方项目](https://github.com/websockets/ws)。这不是当前项目已有的依赖。

`src/start.mjs` 继续仅使用 Node 内置模块，单机独立启动不导入网络服务或额外依赖。联网业务运行代码仍放入 src，Node I/O 适配采用单独的 `.mjs` 边界，工程启动命令放 scripts。服务端与浏览器打包清单分别管理；同步调整 lint / 构建检查以覆盖服务端文件，禁止把服务端代码或凭据打入浏览器产物。

服务端复用当前物理和规则模块，补充无 DOM 的碰撞资产加载。PNG 解码后的法线表必须与浏览器加载结果对照，不能省略碰撞贴图或以简化碰撞代替现有球台。各比赛实例拥有独立模块缓存及求解器状态，首版可使用 Worker 隔离；实际并发上限以 CPU、内存及对局测量确定。

### 同步边界与手感

- 相机、走位、窗口大小与本机帮助界面只影响自己的浏览器。
- 可靠命令包括准备、开局、放球、击球、退出和再来一局。低频瞄准姿态只供对手显示，不决定分数。
- 击球命令提交当前球杆参数，由服务端检查身份、当前席位、比赛阶段、母球位置和参数范围；客户端不提交最终得分或获胜结果。
- 每条修改命令携带命令 ID、比赛 ID、比赛版本和回合编号。服务端去重、拒绝过期命令，并广播已确认结果。双击或重连重发不能产生第二杆。
- 本机按 Space 可以立即进入准备动作，确认通过后才触球；确认迟到时保持安全准备状态，不先改变球局再等待授权。
- 球滚动时推送显示快照并插值，初始目标为每秒 10–20 次，测量后调整；不将网络发送频率替换成物理步长。
- 原物理步长、摩擦、碰撞顺序与规则维持现状。浏览器预览不作为结果依据；每杆结束采用服务端完整稳定快照统一双方球位、统计与球权。
- 比赛快照包含双方统计、规则上下文、母球在手状态、比赛版本和物理状态。仅 `World.serialize()` 不足以重建完整对局。
- 滚动中重连先恢复显示与比赛阶段，等待稳定快照后开放操作；不声称当前序列化可以精确恢复碰撞求解器的中间接触状态。

### 异常策略

联网暂停只打开本机菜单，不能停止服务端球运动；本机回放也不能回写正在进行的比赛。对手仍可查看球台。

掉线后保留席位，建议恢复窗口初值为 30 秒。当前已接受的击球继续完成判罚，下一杆等待重连；重连按原凭据恢复同一席位并取最新状态，不另建第二个玩家。恢复超时结束比赛并标记原因。主动退出与临时掉线分别处理。

比赛中重开改为双方确认的新一局，不沿用单人一键重置。版本或碰撞资产摘要不匹配时不开始比赛。首版房间状态可暂存服务端内存，因此浏览器刷新可恢复，服务进程重启则终止已有房间；跨进程持久恢复列为后续扩展。

服务端校验房间容量、席位凭据、消息大小、命令频率及连接来源。邀请链接包含加入信息，不包含私有席位凭据。玩家名字继续按文本呈现。

## 开发顺序与阶段出口

| 顺序 | 交付                           | 进入下一步的条件                                                               |
| ---- | ------------------------------ | ------------------------------------------------------------------------------ |
| 1    | 同机模型与操作权交接           | 两人独立统计、续杆与换人准确，输入绑定没有重复或串席。                         |
| 2    | 同机完整入口、结果、回放与重开 | 四室内双人专项和现有单机回归通过；这是首个可交付版本。                         |
| 3    | 无界面权威比赛技术验证         | 同组初态与击球命令对照浏览器，碰撞法线、轨迹、判罚一致；两个比赛实例互不影响。 |
| 4    | 房间服务与大厅                 | 两个独立浏览器会话可创建、加入、准备、退出和恢复席位。                         |
| 5    | 联网双人闭环                   | 双方真实击球、放球、判罚、结果与再来一局一致。                                 |
| 6    | 异常与联网手感                 | 延迟、重复命令、后台页面、丢失连接、场景重载及服务关闭都有可解释结果。         |
| 7    | 公网部署验收                   | 完成 HTTPS / WSS 部署、跨设备实测与容量测量，再公布公网入口。                  |

第 3 步是联网架构的关键门槛。目前只有源码可复用性的证据，尚无服务端无界面运行的实测证据。若不能与原球台行为对齐，先修正加载与实例隔离，不以房主浏览器的结算结果替代权威比赛。

网络专项覆盖两个独立玩家会话，而非仅在一个页面伪造远程状态；增加过期回合、重复击球、占满房间、断线重发与两房并行的集成验证。先用受控网络延迟验证一致性，再进行真实局域网和公网双设备测试。公网可达与跨设备手感不能只凭 localhost 测试宣称通过。

运行代码、资源或构建规则改变后执行 `node scripts/check-project.mjs --browser`，并执行受影响的同机、房间、连续玩法与流畅性专项。工程工具改变也执行整体检查。JSON 验证记录放 reports，浏览器产物放 artifacts/testing；冻结 PCOL 文件继续保持原字节与哈希。具体操作遵循[开发流程](workflow.md)。
