# 房间与双人对战面板设计

状态：2026-10-12，用户已确认当前设计可行，保留为后续开发依据；功能实施等待用户后续明确启动。沿用用户选择的「先同机双人，再扩展联网房间」。[交互预览](rooms-panel-prototype.html)是独立设计稿，包含明确标记的模拟球权、房间和结果，不接入游戏、服务或真实计分。当前游戏入口仍是预留面板；实现依据为[开发方案](rooms-and-two-player-plan.md)。

确认范围包括扩宽的One more thing...入口、精简的两位姓名与四套室内选择、Single Play紧凑HUD及暂停菜单、对应室内的开局视角，以及解码后220ms淡入、连续选择只取最新请求、失败保留背景与重试、减少动画支持。联网房间保留为第二阶段设计。设计可行性的确认不替代后续真实同机、联网或浏览器视觉验收；当前实现与验证边界继续以本文件和验证记录为准。

## 设计目标与信息架构

One more thing... 是唯一新增功能入口。保留首页五项菜单的布局、场馆选择及 About；不增加主导航、账户系统或多层大厅。同机模式不需要创建房间、房间码、联网准备或连接服务。

| 层级     | 面板                    | 用户要完成的事                         | 首版范围                   |
| -------- | ----------------------- | -------------------------------------- | -------------------------- |
| 入口     | One more thing...       | 选择同机双人或了解房间                 | 同机卡片在前，房间卡片在后 |
| 同机     | Two-player match        | 填写两位姓名，确认当前场馆，开始一局   | 第一阶段                   |
| 联网     | Rooms                   | 选择创建或加入                         | 第二阶段                   |
| 联网设置 | Create room / Join room | 提交姓名与场馆，或姓名与房间码         | 第二阶段                   |
| 联网等待 | Room                    | 查看两席、场馆、房间码及资源／准备状态 | 第二阶段                   |
| 比赛     | 现有紧凑 HUD            | 确认当前操作者、得分及比赛状态         | 延用现有游戏界面           |
| 赛后     | 现有居中结果面板        | 看双方统计，选择再来一局或退出         | 同机直接重开，联网双方确认 |

预览中的顶部「设计预览」工具条属于评审工具，不进入游戏。可以直接查看任一设计状态，也可以按完整流程操作。房间操作均写明为模拟；首版正式界面仅开放同机入口，ROOMS 保留「ONLINE · NEXT」说明，不提供可提交的创建／加入按钮，待服务闭环通过后一起开放。

## 视觉与布局

One more thing... 使用更宽的右侧面板，突出双人玩法的重要性：桌面宽度取视口的 60%，最小 480px、最大 840px，并始终限制在两侧留白内；例如 1440px 视口为 840px，1280px 为 768px，1014px 约为 608px。场馆与 About 继续保持 480px。桌面四周 24px，480px 以下为 8px。标题与底部操作区固定，正文独立滚动；设置与等待页保持同一宽度，只替换正文，通过 BACK 返回，不叠加抽屉或在跳转时突然改变宽度。

宽屏入口并列呈现两个等宽卡片；同机双人为左侧主卡，使用略亮的深绿底、暖金顶线与清晰动作，房间为右侧次卡。1000px 以下恢复单列，避免在实际面板宽度不足时强行排列。宽屏姓名字段并列，房间码与场馆并列，两位玩家同排显示；窄窗口按原顺序纵向排列。入口只呈现主标题、玩法卡片与操作区，不放眉题、宣传引导或重复的预览说明；评审工具条继续说明模拟范围。联网设置页保留有用途的模式标签与操作说明，同机设置进一步收敛为姓名与室内选择。

沿用 Saira 600／700、深绿 `#0c1512`、暖金 `#c9b587`、暖白 `#f1f0e9`、次要文字 `#a0b0a6`、6px 卡片圆角与细金色边框。仅本面板提高字号与留白：宽屏标题 40px、1000px 以下 32px、480px 以下 28px；卡片标题 28px、正文 16px、辅助文字 14px。宽屏正文左右 32px、卡片间距 20px，不通过放大所有按钮或改变操作规则制造区别。按钮和输入最小高度 44px；主操作用暖金实色，返回与次操作用细边框，退出确认用危险色。

首屏强调「同一台电脑、两位玩家、轮流击球」。两个入口不使用看似可玩的 COMING SOON 卡片；阶段一明确可用范围，阶段二明确开放条件。场馆卡片复用现有四套预览与登记名称，避免将游戏房间和室内场馆混称：Room 表示两席会话，Venue 表示室内场景。

游戏HUD与Single Play共用[game-ui.css](../../src/presentation/styles/game-ui.css)的紧凑布局：顶端10px、左右20px留白，两块358px宽、46px高的独立计分栏；右侧镜像排列，暖金分数格靠近场景中心，双方姓名分居两端，目标球与BRK保持原位置。窄窗口直接沿用现有820／620px断点，缩短计分栏并按需隐藏BRK。当前操作者的姓名以暖金高亮，同时显示目标球，辅助技术读取完整姓名与当前球权；不另放常驻YOUR TURN卡片。

右上操作区沿用Single Play双人布局的62px顶部位置与44px原生按钮，复用Pause／Replay矢量图标；底部右侧显示站立状态的W AIM、X CROUCH与CONTROLS。没有手中球时不显示P PLACE BALL，回放由真实录制数据决定可用性；独立预览无击球记录，Replay禁用。场景内不放大段预览说明，模拟范围只在顶部评审工具条说明。结果继续居中呈现，不转为首页右侧抽屉。

大厅与设置页继续使用室内缩略图；对局与结果页改用对应室内的Single Play真实开局场景帧，显示从大厅切入球台后的初始相机与灯光，取消额外整屏暗色遮罩，仅保留现有底部80px渐变。四套实景由`node scripts/capture-match-opening.mjs`采集：真实点击SINGLE PLAY与AI-1，等待场景、比赛及相机就绪，在初始inHand阶段截取画布；仅截图时隐藏DOM叠层，避免与设计稿HUD重复。不会加载或改写设计稿页面，也不移动相机、调整模型或替换WebGL接口。场景帧位于artifacts/testing/rooms-panel-design，为可重建的本地产物，不纳入Git；记录见[开局场景采集](../../reports/validation/match-opening-scenes.json)。缺少图片时明确保留原背景，评审工具条显示重建命令及重试入口，不将加载失败当作场景已切换。

背景切换采用两个装饰图片层：卡片选择先更新待开局配置，后台加载并解码对应图片；准备完成后保持原图完全可见，在其上以220ms缓出曲线淡入新图，最后交换可见层。缩略图的暗色遮罩与图片属于同一层，进入对局时随图片一起淡出，不先改变遮罩造成亮度突跳。图片保持居中cover，不叠加缩放、位移、模糊或常驻动画；标题、卡片、焦点与滚动位置不参与背景动画。

连续选择使用递增请求版本，仅最新请求可启动下一次过渡。已开始的短过渡先完成，随后直达最新准备好的图片，不逐项播放中间点击；过期加载及错误不能覆盖新选择或弹出过期提示。相同待处理请求合并，八个固定场景资源的解码结果按需复用；失败项不缓存，评审工具条原位提示与重试，画面仍保留原图。减少动画时不做淡入；在过渡中启用该偏好会立即完成当前动画。相同室内返回设置，或对局切换结果，不重复播放同一背景。此逻辑仅用于独立设计稿；正式场馆切换仍通过现有资源加载、场景就绪和恢复流程，不以图片动画替代真实场景加载。

正式双人模式必须复用现有MatchController.enter、GameView、场馆注册及本地相机／输入装配，先完成所选场景加载，再按同一开局过渡进入球台；不把静态背景图接入实际游戏，不为双人模式另建球台、灯光或相机默认值。区别由两位玩家的模型与操作权绑定实现。设计稿场景帧只用于视角示意，不能进行真实走位，也不能代替正式场景和开局过渡验收。

预览Pause打开居中菜单，同机顺序为RESUME／RESTART／CONTROLS GUIDE／QUIT；支持方向键、Tab循环与Escape返回。重开及退出默认聚焦CANCEL，重开保留姓名和场馆并回到原开球者，退出回到首页；Controls从暂停打开时返回暂停，从HUD直接打开时返回原按钮。联网预览不提供单方重开，离开继续使用房间确认。预览的菜单与键盘帮助只演示界面，不启用击球、回放或联网执行；正式实现复用现有组件与控制器生命周期。

## 同机设置与对局

| 内容     | 呈现与行为                                                                                                |
| -------- | --------------------------------------------------------------------------------------------------------- |
| 两席姓名 | PLAYER 1、PLAYER 2 默认值；持久标签与席位序号，不使用 placeholder 代替标签                                |
| 姓名校验 | 首尾去空白、连续空白归并；空值回填默认姓名；最多 20 个 Unicode 码点；不区分大小写的重名提示修改；文本渲染 |
| 室内选择 | 四套实景卡片直接点选，显示名称与编号；单选状态使用暖金边框和勾选标记，切换保留姓名                        |
| 开球     | 首局 PLAYER 1 开球，再来一局交替；不增加随机开球或自选球权，也不放常驻规则卡片                            |
| 操作说明 | 共用一套键鼠、得分续杆与判罚后换人沿用现有 Controls Guide；设置页不重复显示操作说明                       |
| 主操作   | START MATCH；校验成功后提交配置，加载期间禁用重复提交，资源失败原位重试                                   |

设置页正文仅保留两位姓名、室内卡片和必要的错误提示；不显示模式眉题、共用键鼠的引导句、重复的姓名限制说明或规则列表。481px以上两位姓名并排，较窄窗口纵向排列。室内在1200px以上四卡同排，其余窗口采用两列；图片保持16:9，卡片名称、编号与选中标记清晰分层。卡片使用原生单选输入与fieldset／legend，支持Tab聚焦、方向键切换和Space选择，错误出现时仍定位到对应姓名字段。

选择卡片只改变待开局场馆与设计预览背景，保留姓名及焦点，不逐次重载页面。正式实现点击START MATCH时，如所选场馆不同于当前场景，先保存同机草稿（版本、模式、姓名、场馆和返回面板）及一次性启动意图，再通过现有场馆加载流程切换；场景就绪后消费启动意图，避免刷新重复开局。失败恢复设置与重试，取消清除启动意图但保留草稿。草稿不保存分数，不与联网席位凭据共用存储键。独立预览仅模拟配置与背景，不加载真实球台场景；联网等待页的房主场馆变更仍按后续房间流程处理。

换人通过现有HUD的姓名高亮和目标球更新呈现，`[姓名] · YOUR TURN`作为status供辅助技术读取。输入交接由模型和控制器完成；正式面板不自行递增playerIndex。得分续杆不提示换人，球滚动与判罚阶段不可击球。无需每杆点击「确认交接」。暂停、回放、帮助和返回沿用原布局。结果标题为`[姓名] WINS`或DRAW，不使用YOU WIN／YOU LOSE；姓名、得分、单杆、罚分与统计来自真实模型。

同机再来一局保留姓名和场馆、清空本局统计、交换开球者；退出返回首页。重开和未结束比赛退出复用现有确认面板，默认聚焦 Cancel，Escape 取消。

## 后续联网流程

创建：ROOMS → CREATE ROOM → 姓名／场馆 → 提交 → 等待另一席 → 双方资源就绪并准备 → 房主开始。加入：ROOMS → JOIN ROOM → 姓名／房间码 → 服务确认席位 → 同一等待面板。

房间码设计为六位、大小写无关的大写字母与数字，排除 `0 O 1 I`。显示为两个三位组；粘贴允许空格与连字符，提交前归一化。该格式是协议设计约束，服务端须生成并处理碰撞，客户端不生成真实房间码。邀请入口以房间码为基础；服务与域名明确后再提供加入链接。

| 等待面板区域 | 房主                                             | 访客                               |
| ------------ | ------------------------------------------------ | ---------------------------------- |
| 房间标识     | 房间码与 COPY CODE，复制失败可选择文本手动复制   | 同样可见                           |
| 场馆         | 当前缩略图、名称、CHANGE VENUE                   | 只读，标记 HOST SELECTS            |
| 两席         | 自己的姓名与 HOST；另一席空缺或真实玩家          | 自己的姓名与 YOU；对方 HOST        |
| 资源状态     | 独立显示 Loading venue / Ready to prepare        | 同样区分，不以连接成功替代资源就绪 |
| 准备         | READY / CANCEL READY；场馆变更取消双方准备       | READY / CANCEL READY               |
| 开始         | 两席在线、资源就绪、双方已准备才启用 START MATCH | 只读 Waiting for host              |
| 离开         | END ROOM；确认后关闭房间并通知访客               | LEAVE ROOM；确认后释放席位         |

准备操作等待服务确认后才改变真实状态；不乐观打开 START MATCH。房主仅在等待阶段更换场馆，场景重载后用私有凭据恢复席位，并使双方重新加载与准备。首版不转移房主；房主主动关闭后访客返回 ROOMS 并获知原因。刷新、临时掉线、主动退出分别处理，关闭抽屉不能隐式销毁已创建房间。

联网比赛不新增现场聊天、观众列表、公开房间列表或邀请通讯录。对手连接与加载状态进入现有通知／HUD；本机暂停只打开菜单，不能停止服务端球运动。再来一局显示 0/2、1/2、2/2 的双方同意状态，服务确认后创建下一局；一方退出则取消请求并显示原因。

## 状态、错误与恢复

| 场景                             | 主操作状态                            | 用户可采取的动作                           |
| -------------------------------- | ------------------------------------- | ------------------------------------------ |
| 姓名过长／重名／房间码格式错误   | 不发送请求，字段下方解释              | 修改后重新提交，焦点到首个错误字段         |
| 提交中                           | 明确 Creating / Joining，锁住重复提交 | 请求可取消；迟到成功响应必须释放已创建席位 |
| 无服务连接                       | 创建／加入不可用，显示连接失败        | RETRY；同机模式仍可进入                    |
| 房间不存在／已满／已开始／已关闭 | 保留姓名与房间码，显示具体原因        | 修改房间码或返回 ROOMS                     |
| 场馆加载失败                     | 未准备，不可开始                      | RETRY VENUE 或离开，不能伪装就绪           |
| 等待对手                         | 开始禁用，说明缺少另一席              | 复制房间码或关闭房间                       |
| 对手未准备                       | 房主开始禁用，说明待准备              | 自己取消准备或继续等待                     |
| 临时断线                         | 保存席位，下一杆操作受限              | 自动恢复并显示进度；超时转明确结束原因     |
| 恢复超时／服务关闭／版本不兼容   | 不继续开局，保留可解释结果            | 返回 ROOMS；不把掉线显示为正常获胜         |

错误使用原位 `alert`；准备／加入／复制反馈使用 `status`，不依赖颜色区分。短暂状态不能连续抢读。服务恢复时按最新权威状态更新，过期请求响应与旧比赛事件不能覆盖新面板。30 秒恢复窗口沿用实施提案的待验证初值，不在前端写死为结算规则。

## 键盘、响应式与无障碍

抽屉开启后焦点进入首个可操作项；Tab／Shift+Tab 循环包含 input、select、button 与链接，不能继续沿用父抽屉只搜 button 的实现。输入框中的方向键、Home／End、Space 保留编辑行为，Enter 按表单提交；只在入口卡片使用方向键切换。进入子页焦点到第一字段或标题，返回恢复触发按钮；关闭回到 One more thing... 首页入口。

Escape 在普通子页返回上一级；入口关闭抽屉。房间内离开必须确认，比赛退出沿用现有确认。焦点移动采用 preventScroll，超出正文边界时只滚动正文；标题与主按钮始终可达。减少动画沿用 16ms，无常驻闪烁或背景模糊。320／480／720px 窄窗口与 200% 放大时主流程纵向排列，不横向滚动；室内缩略图保持两列，姓名按上述断点排列。这属于桌面布局要求，不宣称移动设备游戏输入已支持。

## 实现边界与开发顺序

| 落点                                                | 职责                                                       |
| --------------------------------------------------- | ---------------------------------------------------------- |
| presentation/ui/more-things-dialog.js               | 模式入口、子页导航、表单、状态呈现及焦点；不处理计分和球权 |
| presentation/styles/interior-more-things.css        | 组件作用域布局，沿用 tokens 与抽屉，不增加全局覆盖         |
| application/controllers/interior-menu-controller.js | 打开、返回、启动配置、场馆重载后的草稿恢复                 |
| application 的同机会话、模型、控制器                | 两位独立玩家、开球顺序、操作权交接与生命周期               |
| 后续 application 房间会话                           | 命令状态、版本及请求取消，不从 DOM 推导对局状态            |
| 后续 infrastructure 联网适配                        | 服务连接、恢复凭据、消息验证与资源加载                     |

先完成同机模型和操作权交接，再接入同机面板、结果与重开，并验证所有室内；之后依次验证权威比赛执行、房间服务与等待页、联网对局与恢复。预览里的「模拟下一回合」和房间评审控件不会进入运行源码。新组件只有在接入可运行流程后才登记 runtime-catalog，避免建立无调用的核心占位模块。

验收分开记录：设计稿的表单、路由、焦点与布局；真实同机的计分、判罚、换人、回放；联网的真实双会话与服务恢复。设计稿测试不能代替后两项。后续运行代码接入时按[开发流程](workflow.md)执行完整浏览器回归与双人专项。
