# WebGL上下文完整恢复

运行`node tests/e2e/context-restoration.test.mjs`。专项覆盖Chrome/Edge、源码/开发/生产及原始、001、002、003四个室内方案，共24个场景。`--smoke`只运行Chrome源码001，写入独立context-restoration-smoke.json，不能代替完整验收。运行源码或构建规则改变后先执行`node scripts/check-project.mjs --browser`。

## 修复边界

Babylon 3.2与PCOL适配器存在四项恢复缺口：自定义HDR立方体纹理没有进入引擎内部纹理缓存；原始HDR加载遗漏samplingMode元数据，重建会变为nearest过滤；冻结PBR材质在着色器重编译后跳过UBO外的球谐光照uniform；旧纹理绑定缓存会使动态画布贴图重建上传失败，造成地面接触阴影变黑。

`src/compatibility/install-hdr-cube-recovery.js`接入引擎已有的场景纹理重建入口，用保留的六面数据重建未被引擎缓存管理的PCOL纹理，保留包装对象和内部纹理对象。`install-scene-recovery.js`在上下文丢失时清除旧绑定并暂存HDR采样信息，恢复时还原原有各向异性判断、使冻结材质下一次绑定重新上传光照参数，并重置场景材质绑定缓存。监听在场景销毁时移除。兼容层使用当前3.2实现的内部接口；引擎版本变化时必须重新验证这些接口。

组合根在适配器完成加载后安装HDR恢复，通过create-recovering-game-view.js继承保留的视图，在场景装配完成后安装监听。恢复时先请求两帧，等真实纹理与着色器重新就绪后再次请求两帧，保证按需渲染的首页也自动刷新。就绪检查在再次丢失或场景销毁时取消；原GameView的构造、更新和场景装配算法不改写。第三方文件、冻结基准、初始材质参数、纹理数据、灯光、物理和游戏时钟不修改。新增兼容ES模块通过源码原生导入及构建工厂图加载，只有browser.js作为classic-script原样交付。

## 验证方法

每个场景暂停测试页的游戏更新，在固定相机位置(-4.5,1.8,5)、目标(0.15,1.3,0)下保持全部游戏及房间网格原有启用状态，连续执行两次真实WEBGL_lose_context丢失与恢复。直接读取同步渲染后的RGBA，要求与恢复前逐通道完全相等；同时核对资源包装/内部对象身份、材质冻结状态、GPU纹理和着色器程序有效性。等待真实纹理加载、编译与场景就绪，不通过固定长延时掩盖失败。测试有30秒恢复期限，失败关闭该测试上下文并保留现场。

随后进入Practice，再次恢复，核对暂停状态下的画面及规则上下文。恢复游戏更新后通过真实鼠标放球、W瞄准、Space击球、Replay播放、重开和返回菜单验证交互，记录回放时长，并核对重开的规则、玩家计数、全部物理球和UI恢复开局。最后在首页闲置状态恢复第四次，仅在测试实例中清除球台frame-diffuse纹理的图片buffer，并给内部URL添加测试查询参数，避开浏览器解码图片复用；服务仍返回原资产字节，检查后还原URL。延迟该响应150毫秒，并断言延迟请求实际发生。仅通过真实渲染事件要求资源就绪后自动提交至少两帧，不调用scene.render、不点击或移动鼠标。测试页只使用既有诊断句柄，不向交付文件加入观察接口，也不替换全局RAF、时钟或WebGL API。

单元测试覆盖实际Babylon场景纹理生命周期、两次重建、未初始化/已销毁纹理、引擎已管理纹理的去重、恢复监听释放、延迟资源的按需重绘及销毁时取消就绪检查。浏览器同时核对每次恢复不增加网格、材质、纹理、UBO和引擎恢复监听。构建测试检查兼容ES模块进入导入图，拒绝无调用的兼容实现。原始场景另外执行五视角冻结PCOL精确对照。

JSON验证结果位于`reports/validation/context-restoration.json`，PNG及失败像素诊断位于`artifacts/testing/context-restoration/`。阴影专项仍独立维护，新增恢复前后完整静态房间严格像素断言；其相机固定且排除动态球/瞄准覆盖物，见[阴影方法](interior-performance.md)。完整恢复专项不排除这些网格。

像素证据限于上述受控相机、viewport和测试浏览器renderer，不代表任意设备与任意视角均逐字节相等；headless WebGL测试不衡量真实GPU性能。静态阴影的历史硬件测量结论保持原范围。
